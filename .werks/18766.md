# OpenTelemetry data: host name lookup is removed in 3.0

key        | value
---------- | ---
date       | 2026-11-17T17:22:44.528174+00:00
version    | 3.0.0b1
class      | feature
edition    | ultimate
component  | telemetry
level      | 2
compatible | no

In Checkmk 2.5 the dynamic host management connection _OpenTelemetry data -
metrics backend_ creates one host for each value of the resource attribute
set in its option _Resource attribute for host name lookup_, and names the
host after that value. This werk describes the change from the point of view
of a single host, which can be one created by this connection or any other
host.

In 2.5 the host attribute _OpenTelemetry data_ selects a host's data partly
by its host name: the setting _Resource attribute for host name lookup_
gives the host the data whose resource attribute equals the host name. This
setting is deprecated in 2.5 and removed in Checkmk 3.0. In 2.5 the host and
folder properties show a deprecation warning where it is used.

In 3.0 a host's OpenTelemetry data is selected by the filters of the
attribute _OpenTelemetry data_, never by the host's name. For hosts with
identity labels, a rule of _OpenTelemetry data routing via identity labels_
narrows down the data further.

The setting of the same name in the Event Console options of the
OpenTelemetry collector is not affected.

## Reasons for the change

Matching data by host name gives hosts the wrong data, or none, when:

* host names are translated, for example converted to lower case or
  stripped of their domain,
* attribute values contain characters that are not allowed in host names,
  so no host can be named after them, or
* several data sources produce the same name.

## Migration to host name template for DCD created hosts

In 2.5 the setting is mandatory as soon as _OpenTelemetry data_ is enabled,
so every object that has the attribute enabled is affected. You cannot
remove the setting in 2.5 without disabling the attribute.

Hosts created by the dynamic host management connection _OpenTelemetry
data - metrics backend_ (renamed to _Telemetry metrics_ in 3.0) keep their
data. In 3.0 the connection names its hosts with host name templates, see
[Werk #22250](https://checkmk.com/werk/22250). The migration turns the host
name lookup for these hosts into the filter `<attribute> = <host name>`. You
don't need to do anything.

One side effect: in 2.5 the connection skipped attribute values with
characters that are not allowed in host names. In 3.0 it replaces these
characters with `_` instead. So after the update the connection creates new
hosts for such values.

## Manual migration needed for non-DCD hosts

For all other objects the migration sets _OpenTelemetry data_ to _Disabled_.
This removes the host name lookup together with the filters you configured:

* For hosts you created manually, their OpenTelemetry services go `UNKNOWN`
  until you configure the data again.
* For folders, every host that inherits the attribute behaves like a manual
  host.
* In the creation rules of piggyback connections, the connection writes
  _Disabled_ onto its hosts on its next cycle, and their OpenTelemetry
  services go `UNKNOWN`.

The migration does not build a filter from the host name for these objects
on purpose. Such a filter would only carry on the matching by name that 3.0
removes, and on a folder or a creation rule no single filter can stand for
the name of each host. For piggyback hosts a filter would not even last: the
connection rewrites their attributes from the creation rule on every cycle.
Disabling the data source makes sure you notice and choose the filters
yourself.

Before it changes anything, the migration that runs during `omd update`
lists the affected hosts, folders and creation rules and asks whether to
continue. If you continue, the migration makes the changes and logs a
message for each changed object. If you abort, the site stays on 2.5, and
you can first disable _OpenTelemetry data_ for objects that no longer need
it. Running `omd update --pre-flight ignore` does the same as continuing.
If only hosts created by the telemetry metrics connection are affected, the
migration continues without asking.

## What you need to do after the update

Enable _OpenTelemetry data_ again for the affected hosts and select their
data with filters, for example the resource attribute `service.name` with
the value `shop-frontend`. For a folder, a filter selects the same data for
every host in it, so set the filters on the hosts themselves.

For piggyback hosts, 3.0 has no replacement, except for those of the Azure
special agent (see below): filters in the creation rule apply to all of its
hosts alike.

## Azure piggyback hosts

For piggyback hosts from the Azure special agent there is a replacement:
the agent sets identity labels on the hosts, and a rule of _OpenTelemetry
data routing via identity labels_ selects the data by those labels. Enable
_OpenTelemetry data_ in the creation rule again and add such a rule for
these hosts. The migration cannot tell whether a creation rule serves Azure
hosts, so you have to do this yourself.
