# ServiceNow: Notifications updated the issue of a different problem

key        | value
---------- | ---
date       | 2026-10-01T06:04:10.130695+00:00
version    | 3.0.0b1
class      | fix
edition    | pro
component  | notifications
level      | 1
compatible | no

The ServiceNow notification plug-in could update the wrong incident or case.
To find an existing issue, it searched for the Checkmk problem ID in the work
notes (incidents) or the user input (cases). This search also matched longer
problem IDs: a notification for problem ID <tt>51378</tt> could be applied to
the issue of problem ID <tt>513789</tt>. The same happened with the
<i>Use site ID</i> option when a site name started with the name of another
site. As a result, recoveries, acknowledgements and downtimes could end up in
an unrelated issue while the correct one stayed open.

New incidents and cases now carry the problem ID in the ServiceNow fields
<tt>correlation_id</tt> and <tt>correlation_display</tt> (value
<tt>Checkmk</tt>), and the plug-in finds issues by an exact match on these
fields. Recoveries, acknowledgements and downtimes of these issues no longer
need the slow work notes search.

Issues created by previous versions are still found via the work notes, now
with an exact match on the problem ID. With their next update they also get
the correlation fields, so no manual migration is required.

<b>Action required:</b> Check the following in your ServiceNow instance:

<ul>
<li>The ServiceNow user configured in the notification rule must be allowed
to read and write the fields <tt>correlation_id</tt> and
<tt>correlation_display</tt> of incidents or cases. Otherwise the plug-in
keeps using the slower work notes search.</li>
<li>If you set <tt>correlation_id</tt> or <tt>correlation_display</tt> via
<i>Custom fields</i> in the notification rule, remove these entries. The
plug-in now overwrites them with its own values.</li>
<li>If other integrations rely on <tt>correlation_id</tt> of issues created by
Checkmk, adapt them. Issues found via the work notes get the new values with
their next update.</li>
<li>On large ServiceNow instances, add a database index on
<tt>task.correlation_id</tt> to keep the lookup fast.</li>
</ul>
