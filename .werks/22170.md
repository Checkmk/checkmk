# Agent bakery names failing plug-ins and bakes all other hosts

Two problems can keep the agent bakery from baking a host: a bakery
plug-in that fails for the host, and a rule that references an agent
file that is missing on the site. Until now, such a problem also kept
other hosts from getting their agent packages, and it was hard to
find on the page _Windows, Linux, Solaris, AIX_.

Now only the affected hosts get no new package. The page lists the
problems before and after a bake. Each entry shows the error message
and the affected hosts and folders, and it names the rule set of a
failing plug-in.

## Before a bake

With an affected host, the buttons _Bake agents_ and _Bake and sign
agents_ stayed unhighlighted, as if all agent packages were up to
date.

Now the page highlights the buttons, and a warning above the agent
list shows the problems.

## During a bake

The bake stopped at the first affected host. Hosts that came later
got no new agent package.

Now the bake creates the packages of all other hosts. The affected
hosts keep their previous package. The bake also removes the packages
of hosts that no longer exist, as a bake without problems does.

## After a bake

A bake with an affected host ended with a crash report. The page only
stated that the last baking operation ran into an exception. The
failing plug-in appeared only inside a traceback.

Now the bake still ends as failed, but it creates no crash report. A
red box on the page shows the problems until you acknowledge the
result. A bake that fails for another reason, for example while it
builds a package, still creates a crash report.

## Other ways to bake

Bakes that do not start from the page also continue after an affected
host.

- The bake at _Activate changes_ (global setting _Automatically
  create monitoring agents_) writes the problems to
  `~/var/log/web.log`.
- `cmk --bake-agents` prints the problems and exits with an error.
- The REST API endpoint for the baking status reports the failure of
  the baking job as before.
