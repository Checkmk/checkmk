# Veeam Backup & Replication: new REST API based special agent

A new special agent for Veeam Backup & Replication (`agent_veeam`) is now available,
querying the Veeam REST API directly instead of relying on the PowerShell-based agent
plug-in. It runs alongside the existing plug-in and can be configured independently.

The special agent requires Veeam Backup & Replication 13.0.1.180 or later (REST API
version 1.3-rev1). Against an older backup server, it stops with an error naming the
required version.

The new special agent currently provides the following services:

- **Backup job %s**, from the `veeam_backup_jobs` agent section (`GET /api/v1/jobs/states`),
  reporting the state and result of each configured backup job.
- **Backup %s**, from the `veeam_backups` agent section (`GET /api/v1/taskSessions`),
  delivered via piggyback to each protected machine. The time since the last backup is
  checked against the *Veeam: Time since last backup* rule, with the same default levels
  as the plug-in's **VEEAM Client** service (30 hours/2 days).
- **Veeam License**, from the `veeam_license` agent section (`GET /api/v1/license`),
  reporting the license edition, status, expiry, support expiry and consumption.
- **Configuration backup**, from the `veeam_config_backup` agent section
  (`GET /api/v1/configBackup`), reporting whether configuration backup is enabled, the
  time since the last successful backup, restore points kept, encryption and the target
  repository.
- **Backup proxy %s**, from the `veeam_proxies` agent section
  (`GET /api/v1/backupInfrastructure/proxies/states`), reporting each proxy's type,
  description, host, and its online, disabled and out-of-date states.
- **Scale-out repository %s**, from the `veeam_scaleout_repositories` agent section
  (`GET /api/v1/backupInfrastructure/scaleOutRepositories`), reporting the number of
  performance extents and their statuses, the capacity and archive tier configuration,
  and the placement policy.
- **Restore points**, from the `veeam_restore_points` agent section
  (`GET /api/v1/backupObjects` and `GET /api/v1/restorePoints`), delivered via piggyback
  to each protected machine, reporting the number of restore points, the age and type of
  the newest one and the malware status. Like the **Backup** services, those of a file
  share backup go to a host named after the share.
- **Backup repository %s**, from the `veeam_repositories` agent section
  (`GET /api/v1/backupInfrastructure/repositories/states`), reporting a backup
  repository's used space, online and out-of-date states, host, path and
  description. Each extent of a scale-out repository is discovered as its own
  service; the scale-out repository itself has no capacity of its own.

The special agent also inventorizes the backup server in the HW/SW inventory, from the
`veeam_server_info` agent section (`GET /api/v1/serverInfo`): its name, build
version, platform, configuration database, registration and installed patches. Reading
this endpoint requires a more privileged role than read-only monitoring. An account
without that role makes the special agent stop; deselect this service (see below), or
grant the role.

You can select which services the special agent fetches: every service can be enabled or
disabled individually in the rule, and all are enabled by default. Deselect the ones you
do not need, for example data your monitoring account cannot read. If a selected service
cannot be fetched — because the account lacks a required Veeam role, or for any other
reason — the special agent stops and reports the error on the host's Checkmk service, so
you can correct the selection or grant the missing permission.

If a host is monitored by both the new special agent and the legacy PowerShell agent
plug-in, the new sections take precedence: `veeam_backup_jobs` supersedes `veeam_jobs`,
and `veeam_backups` supersedes `veeam_client`. On such a host, the corresponding old
services (from the plug-in) disappear once the new special agent is configured, replaced
by the new ones.

The item of the new services is the job name, sanitized as the plug-in does it: spaces
and apostrophes are replaced by underscores. The same job thus has the same item on the
old and on the new services. A *Veeam: Time since last backup* rule with an item
condition therefore applies to the new **Backup** service as it did to **VEEAM Client**.

Still, **Backup job** and **Backup** are new services, not renamed **VEEAM Job** and
**VEEAM Client** services. Existing graphs, performance data history, and any downtimes
or acknowledgements of the old services are lost.
