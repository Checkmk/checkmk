# Fix history leak of external commands to unauthorized users

Livestatus did not check the authorization of external commands in the
monitoring history, the entries of the class "Commands". Users without the
permission "See all host and services" could read these entries for all hosts
and services of a site, for example by adding the column "Log: complete message"
to a copy of the view *Monitor > History > Search history*.

External commands include comments, acknowledgements and downtimes. The
notification module also writes each notification and its result to the history
as an external command. With the Checkmk Micro Core, the history also contains
the commands for the Event Console, for example updates of events. Nagios writes
commands it doesn't know, for example changes of downtimes through the REST API,
to the history as informational warnings, which every user could read. The
entries revealed host and service names, contact names, states, check output,
notification errors and comment texts, including the comments and contacts of
Event Console events.

Livestatus now authorizes external commands like other host and service entries:
a user only sees an external command if the user may see the host or service the
command refers to. All other external commands are only shown to users with the
permission "See all host and services", for example commands for host groups,
global commands and commands that refer to comments, downtimes or events by
their ID. This includes the commands of the notification module, but the
notification entries they add to the history are still shown as before. Warnings
of Nagios about commands it doesn't know now count as external commands. The
history now also shows the host and service an external command refers to, so
filtering the history by host or service finds these external commands, too.

### Who is Affected

All editions are affected, with both the Checkmk Micro Core and Nagios. A site
is affected if users without the permission "See all host and services" can
access the monitoring history, either through the GUI or through any other
Livestatus client that queries the history with `AuthUser`.

### Affected Checkmk Versions

* 2.5.0
* 2.4.0
* 2.3.0 (EOL)

### Vulnerability Management

We have rated the issue with a CVSS Score of 5.3 Medium
(`CVSS:4.0/AV:N/AC:L/AT:N/PR:L/UI:N/VC:L/VI:N/VA:N/SC:N/SI:N/SA:N`) and assigned
`CVE-2026-124847`.

This issue was found during internal review.

### Indicators of Compromise

Check the custom views of your users (*Customize > Visualization > Views*) for
views with the data source "The log file" that show one of the columns "Log:
complete message", "Log: informational part of message" or "Log: comment".
Check their dashboards (*Customize > Visualization > Dashboards*) and, in the
commercial editions, their reports (*Customize > Business reporting > Reports*)
for such views, too.

Users can also show the comments of external commands in the view "Failed
notifications" by changing its filters. The web server's access log
`var/log/apache/access_log` then contains requests for the view
`failed_notifications` with the URL variable `logclass5=on`.

### Mitigations

If updating is not possible, remove the following permissions from all roles
whose users should not see the history of other hosts: "Customize views and use
them", "Customize dashboards and use them", "Log - Failed notifications
(failed_notifications)" and, in the commercial editions, "Customize Reports and
use them". This protects the GUI, but not other Livestatus clients. With Nagios,
the view "Search history" shows the warnings about unknown commands to every
user anyway, so don't send such commands to Nagios sites, for example changes of
downtimes through the REST API.
