# Clustered services are only disabled by rules matching the cluster

key        | value
---------- | ---
date       | 2026-10-05T14:33:50.944427+00:00
version    | 3.0.0b1
class      | fix
edition    | community
component  | checks
level      | 2
compatible | no

This affects users who map services from a node to a cluster with the rule _Clustered services_ and disable some of them with _Disabled services_ or _Disabled checks_.

A clustered service belongs to the cluster, so the cluster's rules decide whether it is disabled.
Service discovery and monitoring did not consistently follow this:

* On the service discovery page of the node, a disabled clustered service was listed under _Disabled services_ with bulk actions, instead of under _Disabled clustered services - located on cluster host_. Enabling it from there reported success but had no effect.
* On the service discovery page of the cluster, the service was shown as vanished or not at all if the rule also matched the node.
* A rule matching only the node disabled the service on the cluster, while both service discovery pages showed it as monitored.

Now a _Disabled services_ or _Disabled checks_ rule disables a clustered service only if it matches the cluster.
The node lists the service under _Disabled clustered services - located on cluster host_, and the cluster lists it under _Disabled services_, where it can be enabled again.
Like other disabled services (see werk #19806), disabled clustered services are no longer written to the autochecks file of the node.

This restores the behaviour introduced by werk #7128, which was lost in Checkmk 2.0.

**Incompatibility:** a rule matching only the node no longer has any effect on a clustered service.
If you have disabled clustered services with such a rule, they are monitored on the cluster after the update.
To keep them disabled, make the rule match the cluster.
