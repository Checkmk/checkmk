# Redfish: an unavailable chassis no longer turns Check_MK CRIT

key        | value
---------- | ---
date       | 2026-10-29T12:38:24.426066+00:00
version    | 2.5.0p19
class      | fix
edition    | community
component  | checks
level      | 1
compatible | yes

Since [Werk #22290](https://checkmk.com/werk/22290), the _Check_MK_
service of Redfish hosts could go CRIT with an error like
`/redfish/v1/Chassis/2 is temporarily unavailable`. This happened
whenever one of several chassis of a device was not ready to answer,
which HPE iLO 5, for example, reports intermittently. On some devices,
such as HPE iLO 4, Cisco CIMC or Supermicro, the same could happen for a
management controller.

The agent now ignores such a chassis or controller in that check cycle
and monitors the rest as usual. If none of them can answer, the
_Check_MK_ service still goes CRIT.

Werk 22290 also caused services to lose their data for a check cycle if
a part of the device, such as a chassis, a system or a storage
controller, could not be queried. These services now keep their last
known data for up to five minutes, provided the _Check_MK_ service runs
at least that often.

The _Firmware health_ service no longer reports "All firmware in optimal
state" if the firmware data could not be queried.
