# REST API: Notification rules reject host tag conditions without tags

key        | value
---------- | ---
date       | 2026-11-12T18:14:29.477142+00:00
version    | 2.5.0p21
class      | fix
edition    | community
component  | rest-api
level      | 1
compatible | no

When creating or editing a notification rule through the REST API, an entry of `match_host_tags` with `tag_type` set to `tag_group` was accepted without the tags to match:

* without `tag_id` for the operators `is` and `is_not`
* without `tag_ids` for the operators `one_of` and `none_of`

Such an entry was dropped without notice.
The rule was stored without this host tag condition, so it matched more hosts than intended.

The REST API now rejects such requests with status code 400 and names the missing field.

This werk is incompatible: scripts that send such entries now fail.
Add `tag_id` or `tag_ids` to the entry, or remove the entry to keep the previous behavior.

Existing rules are not changed.
Checkmk cannot tell which rules were created with such an entry, because the entry was not stored.
If your scripts may have sent such requests, compare the host tag conditions of the rules they created with the conditions you intended, and add the missing ones.
